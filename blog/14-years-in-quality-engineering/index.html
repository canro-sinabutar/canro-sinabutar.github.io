14 Years in Quality Engineering: From Clicking Buttons to Edge AI Architecture

October 7, 2026 · 4 min read

In 2012, my job as a QA Engineer was simple to describe, yet exhausting to execute: open a browser, click a button, check the database, and tick a box in an Excel spreadsheet. If a build broke on Friday, it was usually because a human was too tired to catch a broken UI element on Thursday.

Fast forward to 2026, and the role of Quality Assurance is completely unrecognizable.

Over the last 14 years, I didn't just watch the software testing industry change—my own career transformed right along with it:

  • 2012–2015 (QA Engineer): The Era of Manual Intuition & Test Matrices

  • 2016–2019 (SDET): The Era of Code, Selenium, and CI/CD Pipelines

  • 2020–2022 (QA Lead): The Era of Engineering Strategy & Shift-Left Culture

  • 2023–2026 (Sr. SDET): The Era of Autonomous AI Agents & Edge Hardware Validation

The biggest realization from my 14-year journey? Quality Engineering didn't just get faster—it expanded.

We stopped being gatekeepers who catch bugs at the end of a sprint. Today, we architect self-healing systems, design AI testing pipelines, and validate non-deterministic neural networks running on resource-constrained hardware.

Here is the story of how my role evolved, the hard lessons learned at each stage, and where Software Quality is heading next.

1. 2012–2015: The Manual Era — Intuition, Test Matrices, and Human Limits

When I started my career in 2012, Quality Assurance was largely a downstream safety net. Developers built features, pushed code to a staging environment, and handed it over to QA to "find bugs" before release day.

My core tools were simple: Excel spreadsheets, Jira, and web browsers. A typical day consisted of:

  • Writing exhaustive test matrices covering every positive and negative workflow.

  • Executing repetitive regression suites by hand before every production deployment.

  • Relying heavily on exploratory testing to discover unexpected edge cases that documented requirements missed.

The Reality Check:

Manual testing was irreplaceable for evaluating real human experience, user flow intuitive friction, and visual alignments. However, as software development shifted toward two-week Agile sprints, manual regression hit a mathematical wall. Running a 300-step regression matrix by hand every single sprint was not only slow—it was prone to human fatigue.

2. 2016–2019: Transitioning to SDET — Code, Locators, and Pipeline Automation

As release cycles accelerated, my focus shifted from executing tests to writing software that tests software. I stepped into the role of Software Development Engineer in Test (SDET).

This era was defined by building robust test automation frameworks using Selenium WebDriver, JUnit, TestNG, and later Appium for mobile apps.

What Changed:

  • Page Object Model (POM): Architecting clean test frameworks where UI elements and test logic were strictly separated for maintainability.

  • CI/CD Integration: Wiring automated suites into Jenkins and GitLab CI pipelines so tests ran automatically on every pull request.

  • API Testing Shift: Moving lower down the testing pyramid to validate REST APIs using REST Assured, catching business logic bugs before UI execution.

The Major Bottleneck:

Automation solved the speed problem, but created a massive maintenance problem. Dynamic element locators broke continuously when UI code changed. SDETs often spent 60% of their sprint capacity repairing flaky tests and fixing broken locators rather than expanding coverage.

3. 2020–2022: QA Leadership — Shift-Left Strategy & Quality Governance

Moving into a QA Lead role changed my perspective entirely. I realized that quality is not something you "test into" a product at the end; it is something you design from the beginning.

My responsibility expanded from managing test scripts to orchestrating engineering culture and metrics across cross-functional teams.

Key Initiatives as Lead:

  • Shift-Left Culture: Involving QA engineers in early architecture discussions and product grooming sessions to catch logic gaps before code was even written.

  • Developer-Friendly Tooling: Transitioning teams to modern Node/TypeScript-based tools like Cypress and Playwright, which provided auto-waiting, network interceptors, and faster execution feedback loops.

  • Flaky Test Elimination: Establishing strict engineering guidelines to isolate and quarantine non-deterministic tests, restoring developer trust in CI/CD pipeline stability.

4. 2023–2026: Senior SDET — Autonomous Agents & Edge AI Intelligence

Today, as a Senior SDET, the testing landscape has undergone its most profound transformation yet: the convergence of Generative AI and Edge Hardware Computing.

Testing is no longer limited to executing rigid, deterministic scripts against a web browser running in a cloud server.

Autonomous AI & Self-Healing Engines

Instead of hardcoding dynamic DOM locators, modern testing frameworks leverage LLMs and Vision-Language Models (VLMs). If a button ID changes in production, the AI agent evaluates visual cues, historical element positions, and intent to auto-heal selector paths in real time without breaking the build pipeline.

Edge AI & Hardware-in-the-Loop (HIL) Validation

The current frontier requires validating intelligent models deployed directly on resource-constrained Edge hardware (NPUs, automotive microcontrollers, mobile devices, and IoT hardware).

Validating Edge AI introduces entirely new quality dimensions:

  • Quantization Accuracy: Verifying that compressing cloud models from 32-bit floats (FP32) to 8-bit integers (Int8) doesn't create unacceptable accuracy drift or safety edge-case failures.

  • Hardware Constraints: Monitoring inference latency (<10 ms) under thermal throttling, voltage drops, and RAM limitations using Hardware-in-the-Loop (HIL) test setups.

  • Network Disruption: Stress-testing local fallback mechanisms during intermittent connectivity or total network blackouts.

Key Lessons From a 14-Year Journey

Looking back from 2026, tools and technologies have completely morphed, but the core objective of Quality Engineering remains unchanged: mitigating risk and protecting the user experience.

  1. Tools change, engineering principles stay: Whether you write Selenium scripts in 2016 or design Edge AI testing rigs in 2026, understanding system architecture and failure modes is what makes a great SDET.

  2. Quality is a collective culture: A lead's job is not to build a bigger testing team, but to enable the entire engineering team to ship reliable code faster.

  3. Embrace the shift: Moving from manual execution to AI orchestration didn't eliminate QA—it elevated us into system architects.
